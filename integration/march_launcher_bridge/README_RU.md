# MARCH ROLE PLAY — вход и регистрация через лаунчер

Это **локальный прототип интеграции** для ситуации, когда **Windows-лаунчер и MTA-сервер запущены на одном компьютере** и игрок подключается к `127.0.0.1:22003`. Для публичного RP-сервера с удалёнными игроками потребуется отдельный защищённый серверный API (HTTPS, одноразовая сессия с доказательством владения, защита от перебора).

## Что сделано

- В лаунчере включены формы входа/регистрации; пароль не записывается в JSON-настройки.
- По кнопке **ВОЙТИ** или **ЗАРЕГИСТРИРОВАТЬСЯ** данные помещаются в память на **5 минут**.
- При подключении MTA локальный ресурс `march_launcher_bridge` забирает данные **один раз** через `http://127.0.0.1:28745/pending`, проверяет их на сервере и вызывает стандартное `logIn`.
- Результат приходит обратно в лаунчер; если вход прошёл успешно, пароль очищается из полей.
- В лаунчере `Запомнить логин` хранит **только имя**, но никогда не хранит пароль.

## Важное ограничение существующего march_auth

У проекта уже есть ресурс **`march_auth`**, который может хранить аккаунты в **`march_accounts.db`** с bcrypt. **Его исходный server.lua не находится в репозитории лаунчера.**

Предоставленный `march_launcher_bridge` использует **штатные MTA-аккаунты** `getAccount`, `addAccount`, `logIn`. Он не создаёт новую собственную базу, но *не знает* схему `march_accounts.db` и не умеет проверять её пароли. При обнаружении отдельной базы регистрация сознательно блокируется сообщением `custom_auth_not_integrated`, чтобы не создавать несовместимые дубли.

**Чтобы связать логин и регистрацию именно с существующей базой `march_auth`, нужно обновить его реальный server.lua и meta.xml.** Не копируйте базы, не удаляйте `march_accounts.db`, не создавайте вторую таблицу аккаунтов и не переносите проверку пароля в WPF-лаунчер.

Если `march_auth` уже использует нативные MTA-аккаунты как единственный источник авторизации и не содержит отдельную SQLite-базу, этот ресурс можно проверить как есть.

## Установка в локальный MTA-сервер

1. Скопируйте папку `march_launcher_bridge` целиком в `mods/deathmatch/resources/`.
2. В консоли MTA-сервера:
   - `refresh`
   - `start march_launcher_bridge`
   - `aclrequest list march_launcher_bridge`
   - `aclrequest allow march_launcher_bridge all` (предоставляет только права, запрошенные в meta.xml)
   - `restart march_launcher_bridge`
3. Запустите сервер, Discord (необязательно) и **новую версию лаунчера** на том же ПК.
4. В лаунчере введите логин и пароль, нажмите **ВОЙТИ** (или **ЗАРЕГИСТРИРОВАТЬСЯ**), после этого **ИГРАТЬ**.
5. Если ресурс и аккаунты совместимы, после входа в MTA сервер вызовет `onPlayerLogin` автоматически и подтверждение появится в лаунчере.

### Если окно `march_auth` осталось поверх игры

Серверный `logIn` не гарантирует закрытие DX/CEF-панели, если её код всегда принудительно показывает форму. В клиентском коде **оригинального** `march_auth` перед открытием панели добавьте проверку:

```lua
if getElementData(localPlayer, "march:launcherAuth") == true then
    -- Здесь вызвать уже существующую функцию закрытия панели
    -- и продолжить обычную инициализацию авторизованного персонажа.
    return
end
```

На случай, когда панель уже открыта, слушайте `onClientElementDataChange` для ключа `march:launcherAuth` и вызывайте ту же функцию закрытия панели. **Это только подсказка для интерфейса**, не источник полномочий: проверка реальной авторизации должна остаться на сервере через `getPlayerAccount`/существующее состояние `march_auth`.

## Безопасность

- `127.0.0.1:28745` слушает **только loopback** Windows. Пароль передаётся только между локальными процессами и один раз, без логирования или сохранения на диск.
- MTA-скрипт не применяет автоматическую авторизацию к игрокам с **удалённым IP**. Нельзя заменять это проверкой только ника игрока или доверять клиентским element data.
- Если `fetchRemote` не может достучаться до loopback API, обычный вход внутри игры остаётся доступен.
- **Не используйте локальный мост для публичного сервера.** Это не замена сетевой архитектуре одноразовых токенов и HTTPS.
- Регистрацию и вход с привязкой к уже существующей `march_accounts.db` необходимо реализовать в самом `march_auth`, сохранив прежние bcrypt-хеши и данные игроков.
